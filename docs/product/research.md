# Implementation-planning research

**Historical:** This research concerns the superseded Image Evidence Scanner and does not support DocShield architecture or model decisions. DocShield-specific research has not yet been conducted. Sources below are retained for project history only.

Research for the former image-scanner technical choices; evidence is not a product decision. Sources checked 2026-11-24 and 2026-11-25.

## Findings

### CLI/runtime and tests

- **Evidence:** Python provides built-in `argparse` for CLI parsing and `venv` for isolated environments. `pytest` documents a conventional `src/` layout and test execution with `python -m pytest`. [Python argparse](https://docs.python.org/3/library/argparse.html), [Python venv](https://docs.python.org/3/library/venv.html), [pytest good practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)
- **Recommendation:** Python is a low-friction CLI/runtime candidate for image/model ecosystem integration; use stdlib `argparse` and `pytest`, avoiding a new CLI framework until needs justify it. This is not an evaluation of packaging/install UX or native distribution.

### Bounded JPEG/PNG decode

- **Evidence:** Pillow supports JPEG and PNG, opens lazily (header identification before pixel loading), and has `MAX_IMAGE_PIXELS` decompression-bomb warning/error behavior. Its documented pixel default is a library safeguard, not this product’s 50-million-pixel contract. [Pillow image API](https://pillow.readthedocs.io/en/stable/reference/Image.html), [Pillow formats](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html)
- **Recommendation:** Pillow is a plausible decoder if the implementation restricts format explicitly to JPEG/PNG, checks dimensions before `load()`, sets the configured bound to the SPEC policy, treats the warning as an error, checks frame count, and retains built-in safeguards. Enforce byte-size and wall-clock/resource bounds separately; pixel count alone does not bound parser time or all memory use.

### Broad metadata

- **Evidence:** ExifTool’s first-party format tables list read support across EXIF, GPS, IPTC, XMP, ICC profiles, JPEG and PNG; its JPEG documentation covers APP segments including EXIF/XMP. [ExifTool supported formats](https://exiftool.org/#supported), [ExifTool application docs](https://exiftool.org/exiftool_pod.html)
- **Evidence:** C2PA is a distinct signed provenance format; ExifTool’s support for recognizing C2PA/JUMBF metadata does not by itself perform C2PA signature/trust validation. The C2PA SDK advertises parsing and validating embedded manifests. [ExifTool supported formats](https://exiftool.org/#supported), [C2PA Rust SDK](https://github.com/contentauth/c2pa-rs)
- **Recommendation:** Evaluate ExifTool as a broad read-only metadata backend, with versioned output and an explicit allowlisted invocation; independently bound subprocess time/output and capture errors. Verify fields/coverage on representative JPEG and PNG fixtures. Parser support does not guarantee every unknown block/value is exposed, so SPEC’s coverage contract still needs a defined inventory.

### Offline C2PA validation

- **Evidence:** The official C2PA Rust SDK supports parsing and validating manifests, with configurable settings/context and trust anchors. C2PA guidance explains that signer trust depends on configured trust lists and revocation services/status. [c2pa-rs](https://github.com/contentauth/c2pa-rs), [SDK settings guide](https://opensource.contentauthenticity.org/docs/sdk-repos/c2pa-cpp/docs/context-settings), [C2PA guidance](https://spec.c2pa.org/specifications/specifications/2.4/guidance/Guidance.html)
- **Evidence:** The official `c2pa-python` binding reads and validates media through `Reader`, accepts file or stream inputs, and supports per-instance `Context` settings. Its settings explicitly disable remote manifest retrieval and OCSP with `verify.remote_manifest_fetch: false` and `verify.ocsp_fetch: false`; the docs describe these as disabling network-dependent features for offline use. The binding requires Python 3.10+. [c2pa-python](https://github.com/contentauth/c2pa-python), [usage](https://github.com/contentauth/c2pa-python/blob/main/docs/usage.md), [context/settings and offline operation](https://github.com/contentauth/c2pa-python/blob/main/docs/context-settings.md)
- **Recommendation:** Use the Python binding with both network-dependent verification settings explicitly false, a local input stream, and no remote trust-list configuration. Report manifest validity, signer trust, and revocation freshness separately. Keep process-level network-denial testing because configuration intent is not runtime observation.

### Local model runtime and weight safety

- **Evidence:** ONNX Runtime is designed to load and run a local model path; it exposes `disable_telemetry_events()`, which only documents disabling telemetry—not all possible networking. [ONNX Runtime Python API](https://onnxruntime.ai/docs/api/python/api_summary.html), [ONNX Runtime privacy](https://github.com/microsoft/onnxruntime/blob/main/docs/Privacy.md)
- **Evidence:** PyTorch’s serialization documentation describes `weights_only=True` loading to restrict unpickling behavior. That is a risk reduction, not proof that an arbitrary artifact is safe or that the model cannot consume excessive resources. [PyTorch serialization notes](https://docs.pytorch.org/docs/stable/notes/serialization.html)
- **Recommendation:** Prefer a fixed, locally supplied ONNX artifact and ONNX Runtime for inference if selected candidate models export correctly; it separates inference from training dependencies. Do not download weights/code at scan time. Verify artifact hashes against a locally supplied manifest, pin model/runtime versions, and test with network denied. Avoid accepting arbitrary pickle/model code. Evaluate task accuracy, licenses, hardware support, and ONNX conversion on actual candidate detectors before selection.

### Metadata parser deployment

- **Evidence:** ExifTool's official installation guidance supports running its Perl distribution without a system-wide install and documents broad EXIF/GPS/IPTC/XMP/ICC support. Its command-line documentation provides unknown-tag options and JSON output. [ExifTool installation](https://exiftool.org/install.html), [supported formats](https://exiftool.org/#supported), [application documentation](https://exiftool.org/exiftool_pod.html)
- **Decision context:** The project chose ExifTool as a separately installed runtime dependency, invoked with fixed arguments and bounded timeout/output; no scan-time download or bundled executable. If absent, the report exposes unavailable coverage rather than pretending extraction succeeded.

### Network-free execution

- **Evidence:** A runtime’s offline/local-model API or telemetry opt-out is not a system-wide network prohibition; the reviewed ONNX Runtime API only promises telemetry-event disablement. C2PA validation may depend on configured revocation/trust behavior.
- **Recommendation:** Treat “no network” as a process execution invariant: deny outbound networking in integration tests (OS/network namespace or equivalent), exercise scan paths including C2PA and model initialization, and fail tests if any connection is attempted. Require models, trust lists, and reference data to be explicit local paths. Build/install dependencies before scan time; no runtime fetch/update path.

## Unresolved / evidence limits

- No concrete generation/edit detector was selected or validated; neither model quality, licensing, hardware feasibility, nor release targets can be established from runtime documentation.
- The exact parser behavior for malformed/oversized EXIF, XMP, IPTC, ICC, and nested container blocks needs adversarial fixture testing; documentation feature lists are not resource-bound guarantees.
- Confirm the pinned C2PA Python binding version, trust-list provenance/update process, revocation behavior, and network behavior empirically on the supported runtime.
- Numerical operational memory/time bounds on the selected feasibility reference hardware remain open; SPEC gives input-size/pixel ceilings but not a scan-time budget.

## Consumer-image detector feasibility proposal (2026-11-25)

This section responds to the target population and reference machine in `docs/product/decisions.md` §§16–19. Recommendations below are proposals for owner review only; no detector, weight, threshold, or dataset is approved. **Generation detection and AI-edit/manipulation detection are different tasks and must not share a label or release claim.** In particular, a full synthetic-image classifier does not establish sensitivity to localized AI edits, and a manipulation/localization model does not establish detection of fully synthetic images.

### Fully synthetic-image detection

- **Evidence — Universal Fake Detect (UFD):** The first-party CVPR 2023 repository provides pretrained CLIP ViT-L/14 plus a trained linear head; the authors describe cross-generator evaluation, with training data and published test domains covering GAN and diffusion images. Its repository code is MIT licensed. It relies on PyTorch/torchvision, and the released artifact is a `.pth` checkpoint; no maintained ONNX artifact or export path is documented. Its “universal” claim is not evidence against today’s generators, smartphone-camera positives, common AI edits, or the project’s exact sensitivity/FPR gates. [UFD repository and evaluation instructions](https://github.com/WisconsinAIVision/UniversalFakeDetect), [paper](https://arxiv.org/abs/2302.10174)
- **Evidence — DIRE:** The first-party ICCV 2023 implementation reconstructs images with a diffusion model, then classifies reconstruction error. It publishes a diffusion-focused benchmark and reports robustness to perturbations; the tested population is not consumer-camera versus contemporary synthetic/edited images. Its inference path requires PyTorch CUDA 11.7-era dependencies and diffusion reconstruction, not a small single-pass classifier; repository archive status is read-only. No repository license is stated in the visible project materials, and the linked dataset/weight download does not establish redistribution rights. [DIRE repository](https://github.com/ZhendongWang6/DIRE), [paper](https://arxiv.org/abs/2303.09295)
- **Evidence — GenImage:** The official benchmark contains over one million fake/real pairs, with named generators including Midjourney, Stable Diffusion, ADM, GLIDE, Wukong, VQDM, and BigGAN. It reports substantial cross-generator degradation (e.g., average accuracies of 66.9–70.3% for several tested methods) and sharp degradation under JPEG/low-resolution conditions in some model/method combinations. Its published benchmark covers useful historical generators but not the requested camera-capture and modern ordinary-edit distribution. The dataset is provided under CC BY-NC-SA 4.0 with additional terms, so it is not a clean default for a product with potentially commercial use. [official repository, benchmark tables](https://github.com/GenImage-Dataset/GenImage), [dataset license](https://github.com/GenImage-Dataset/GenImage/blob/main/License)
- **Assessment:** UFD is the most practical *candidate for a feasibility experiment* among these sources because it is a single-pass classifier and has published unseen-generator testing. DIRE is a useful comparison/research baseline, but its reconstruction pipeline and older dependencies make it a less attractive local CLI candidate. Neither has credible held-out evidence matching the project’s full required population, ordinary resize/recompression slices, and sensitivity ≥80% at FPR ≤5%; neither reports the project’s ECE ≤0.05 calibration gate on an independent named consumer population. This is explicitly **not a claim that either fails**—it means their available evidence does not establish a pass.

### AI-edited/manipulated-image detection

- **Evidence — TruFor:** The first-party project presents a general image-manipulation detector with image-level confidence and pixel localization, using RGB and learned noise-sensitive features. The project page/paper report broad manipulation benchmarks, but do not establish the consumer AI-edit target population or this project’s held-out operating-point gates. The official project distributes inference code/model artifacts; the reviewed sources do not establish a product-compatible weight license or an ONNX-supported deployment path. Treat both as unresolved pending direct review of the exact repository and artifact terms. [TruFor project page](https://grip-unina.github.io/TruFor/), [paper](https://arxiv.org/abs/2212.10957)
- **Evidence — NIST OpenMFC:** Its official task definition treats manipulation detection as deliberate modification, including splicing/cloning, and has a separate deepfake/GAN task. This validates the need to keep task definitions separate. It is not an available public training corpus: the official site says evaluation data are not publicly released, registration and a data license are required, and past datasets are controlled access. It therefore cannot be assumed usable for this project’s training or local held-out validation. [OpenMFC task/data terms](https://mfc.nist.gov/)
- **Dataset fit:** GenImage mainly labels fully generated images, not localized edits. FaceForensics++ is face-video/frame manipulation with restricted dataset terms, not broad consumer still-image AI edits. COCO is a source of real images, not edit labels; its terms note that the consortium does not own the underlying photos, so image-level reuse rights must be checked rather than inferred from annotation licensing. OpenMFC is access-controlled. These sources do not presently establish a rights-clear, representative, paired corpus of current AI-edited consumer images plus genuine camera positives and edit masks. [FaceForensics++ repository/terms](https://github.com/ondyari/FaceForensics), [COCO terms](https://cocodataset.org/#termsofuse), [OpenMFC](https://mfc.nist.gov/)
- **Assessment:** No reviewed candidate/corpus combination has credible held-out evidence for AI-edited consumer images, including localization if requested, and the project’s specified operating point. Recommendation: evaluate manipulation detectors as a separate, initially experimental workstream, and first establish data access, labels, and redistribution rights. Do not substitute classical splicing benchmark performance for AI-edit evidence.

### Runtime, license, and reference-hardware feasibility

- **Evidence:** UFD and DIRE official inference instructions use PyTorch; this is evidence of a usable GPU inference route, not proof that the models fit 6 GB VRAM or meet latency requirements. ONNX Runtime documents CUDA Execution Provider support, compatibility constraints tied to CUDA/cuDNN package versions, and a configurable GPU memory arena; those runtime capabilities do not demonstrate that these model graphs export or execute correctly. The reviewed candidate repositories provide no maintained, validated ONNX package for the model weights. [UFD](https://github.com/WisconsinAIVision/UniversalFakeDetect), [DIRE](https://github.com/ZhendongWang6/DIRE), [ONNX Runtime CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)
- **Recommendation — licenses:** Resolve code, pretrained-weight, and dataset licenses independently before distribution. UFD’s MIT code license alone does not certify every upstream pretrained component or dataset; DIRE does not make weight/data redistribution rights clear in the reviewed repository; GenImage’s noncommercial/share-alike dataset terms are a material limitation. For TruFor, verify the exact license files and checkpoint terms directly before even an internal product prototype. If provenance of an artifact/permission cannot be verified, do not bundle or redistribute it.
- **Recommendation — measurement plan:** On the specified Ryzen 9 5900HS / 16 GB / RTX 3060 Laptop 6 GB machine (feasibility reference only, not minimum hardware), record OS/driver/CUDA/cuDNN, Python/runtime and model hashes; benchmark CPU and GPU separately. Warm model load, measure cold-start and warmed single-image latency, five sequential images, peak process RSS, peak GPU allocation/VRAM, throughput, and failures across a fixed-resolution range including maximum permitted dimensions. Record preprocessing, resize policy, batch size, and whether GPU memory is shared. Set budgets only after owner review of measured distributions; do not infer them from nominal hardware specs. For DIRE, report reconstruction passes and full end-to-end timing separately. If testing ONNX, export from exact pinned upstream source, compare logits against PyTorch on a fixture set, and verify CUDA and CPU providers; absent a validated conversion, prefer PyTorch over speculative export work.

### Proposal and material gaps

- **Recommendation for owner approval:** Permit a bounded feasibility/evaluation spike, not implementation approval: test UFD as a fully-synthetic candidate; separately screen TruFor or a more directly AI-edit-trained manipulation model for edited-image detection; use DIRE only as an optional computationally expensive generation baseline. Keep all outputs experimental/inconclusive until the project’s prespecified per-slice gates are met on a genuinely held-out, named consumer-image population.
- **Not established:** current generator/edit tool coverage; consumer camera source and demographic/content balance; label provenance; independent identity/source partitioning; paired/unpaired edit corpus rights; ordinary resizing/JPEG quality ranges; robustness against post-processing; benchmark leakage; model and weight redistribution rights; runtime/ONNX conversion; reference-machine latency/RAM/VRAM; score calibration and ECE; and candidate compliance with the 80% sensitivity/5% FPR gate.
- **Stop point:** This is a proposal for the owner. Dataset selection, threshold choice, model approval, and implementation remain open.
